# Verification is the job: a position on agentic development practice

*COMP8020 critical research note. Harshit Gupta, November 2026.*

The claim that agentic coding makes developers faster is both true and beside the point. Peng et al. (2023) found that recruited developers with GitHub Copilot finished a scoped JavaScript task 55.8% faster than a control group. METR's randomised trial of sixteen experienced open-source contributors working on their own repositories found the opposite: tasks took 19% longer with AI tools, against the developers' forecast of a 24% speedup, a belief they still held after the trial (Becker et al., 2025). The studies measure different work, and METR's own account of the slowdown lists low reliability and tacit repository knowledge alongside the time spent checking output; verification is part of the gap, not all of it, and the part this note is about. My position is that what agentic development changes is not how fast code is written but who establishes that it is right. The engineer's job moves from producing code to producing the conditions under which code can be shown wrong, and to deciding when to stop looking.

The literature on assistants already shows the cost moving. Mozannar et al. (2024) had twenty-one programmers label their own Copilot sessions; about a fifth of their time went to verifying suggestions. METR's developers spent nearer a tenth reviewing and cleaning output and were still slower, which says the cost is not the minutes spent reading but the decisions the reading cannot settle. The security results make that concrete. Roughly 40% of the 1,689 programs Copilot produced in scenarios built around high-risk CWE categories were vulnerable (Pearce et al., 2022), and in a controlled user study participants with an assistant wrote less secure code on four of five tasks while being more likely to believe it secure (Perry et al., 2023), the misjudgement METR's developers made about their own speed. None of these studies looked at agents; my inference is that whole-feature generation raises code per unit of attention and leaves the reviewer's confidence exactly where Perry and METR found it.

Bainbridge (1983) named the trap forty years earlier. Automate the routine work and the human is left monitoring a process they no longer practise, expected to intervene exactly when it fails. A developer who reads agent diffs all day is that operator. My final project's answer was not to read harder but rules the agent couldn't quietly weaken: every behaviour a test committed red before its code; a reviewer and a breaker with no part in the work and no power to approve; findings fixed in commits that name them. Those gates found what a green suite hid, once a red-spec commit that had dropped a timing bound so a count would pass, caught by reading the diff against the rule, not by running anything. This does not escape Bainbridge: a reviewer agent is one more layer the human monitors rather than practises. What the harness buys is a smaller surface for judgement, a rule and the diff that breaks it, a task a person can stay practised at.

A harness is only as good as its targets, which is where judgement can't be delegated. Strathern's (1997) phrasing of Goodhart's law, that a measure which becomes a target ceases to be a good measure, describes an agent precisely: it optimises what is tested. When I set a fight-length target of "the player sees all three boss phases", the agent delivered a long, easy boss: nothing measured whether a player who ignored the mechanics lost, and a later playtest showed one pressing a single defensive button all fight still won. SWE-bench is the same proxy at scale: "resolved" means the pull request's tests pass, which its authors say is not enough on its own to guarantee reliable performance (Jimenez et al., 2024). Choosing what the harness measures is the design decision; everything downstream is automation.

Review does not converge on its own, and Strathern says why: review is a measure with findings as its target, so it keeps producing them, and a practice that cannot stop has stopped verifying and started scoring. Each confirm pass in my project found a subtler case than the last, ending in Unicode look-alikes for a name check that protected nothing; what ended it was a written ruling on which property mattered and which findings were now risks. Parnas and Clements (1986) argued that documentation should present the rational process no real design followed; in agentic work that record is also what a reviewer checks a change against, so intent that is not written is intent that is not verified. When my concern about difficulty existed only in a chat, a fresh agent's whole-repository review ranked it nowhere among forty candidates; once written down, it became the next phase.

So the practice I would defend is narrow. Write the tests the agent can fail. Keep reviewers that cannot approve. Put intent where the next reader will find it. Own the targets, and own the stopping rule. The productivity numbers will keep moving with the tools. What has not moved, from completion to the agents METR measured, is that establishing correctness is where the cost sits, and the two parts that cannot be delegated are choosing what counts and deciding when to stop.
